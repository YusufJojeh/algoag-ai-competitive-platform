| البند | الحالة |
|--------|--------|
| **نوع المشروع** | Laravel 12 + React + Inertia + Ollama: مساعد خوارزميات، محاكاة أداء، حل Codeforces (Ollama + Job)، بنك مسائل/مسارات/إرسالات |

### ٣.٢ تحليل الطبقات

| الطبقة | الملفات/المكونات | الجودة | الملاحظات |

| **العرض (View)** | `resources/js/Pages/*.jsx`, `app.blade.php` | جيدة | مكونات وظيفية، لا تقسيم فرعي للمكونات المشتركة |
| **التحكم (Controller)** | `AlgorithmAssistantController` | جيدة | مسؤوليات واضحة؛ يمكن استخراج Form Requests للتحقق |
| **الخدمات (Services)** | `OllamaService`, `BenchmarkRunner`, `CodeforcesSolverService` | جيدة | `OllamaService::generate` طلب POST واحد غير متدفق (`stream: false`) مع مهلة قابلة للتمرير |

### ٣.٣ جودة الوحدات/الموديولات

| الموديول | التماسك | الاقتران | إعادة الاستخدام |
|----------|---------|----------|-----------------|
| OllamaService | عالي | منخفض (Config + Http) | قابل لإعادة الاستخدام في مشاريع أخرى مع Ollama |
| BenchmarkRunner | عالي | منخفض | مقيّد بمفاتيح محددة؛ يمكن تعميمه بمزيد من المفاتيح |
| AlgorithmAssistantController | متوسط | متوسط مع الخدمات والنموذج | مرتبط بسير العمل الحالي |
| الصفحات (Home/Suggestions/Results) | جيد | مرتبط بـ Inertia وـ props | مكونات الصفحة غير مجزأة لمكونات أصغر قابلة لإعادة الاستخدام |

### ٣.٤ الديون التقنية المحددة

1. **OllamaService::generate**  
   طلب `/api/generate` واحد غير متدفق؛ المعامل الثاني هو **المهلة بالثواني** (ليس تفعيل streaming). أي دعم streaming حقيقي للمتصفح يحتاج تصميماً لاحقاً (SSE/WebSocket).

2. **عدم وجود Form Request منفصل**  
   التحقق في الـ Controller مباشرة؛ نقل القواعد إلى `SuggestRequest` و`BenchmarkRequest` يسهل الاختبار وإعادة الاستخدام.

3. **عدم وجود طبقة API**  
   إن رغبت مستقبلاً في تطبيق جوال أو طرف ثالث، ستحتاج مسارات API منفصلة ومصادقة (مثلاً Sanctum).

4. **اعتماد الواجهة على هيكل props ثابت**  
   لا توجد أنواع TypeScript أو وثائق لـ props الصفحات؛ يزيد احتمال أخطاء عند تغيير الـ backend.

5. **حجم الـ benchmark ثابت**  
   `runAll()` يستخدم `BenchmarkRunner::DEFAULT_RUN_ALL_SIZE` (1000)؛ التوثيق في صنف `BenchmarkRunner` يوضح أن المقاييس تركيبية ولا تقارن حلول المستخدم بلغات أخرى.

### ٥.١ الأمان

| البند | الحالة | التوصية |
|--------|--------|----------|
| CSRF | مفعّل (middleware web) | الإبقاء عليه |

| التحقق من المدخلات | موجود (طول وحقول مطلوبة) | إضافة تحقق أقصى لحجم `suggestions` (مثلاً 20 عنصراً) |

| رؤية الجلسات | أي زائر يرى أي جلسة عبر `/session/{id}` | للإنتاج: ربط الجلسات بمستخدم أو token |

### ٥.٢ الأداء

| البند | الحالة | التوصية |
|--------|--------|----------|
| استعلام الصفحة الرئيسية | استعلام واحد + limit 10 | جيد |

| التخزين المؤقت | غير مستخدم للصفحات أو Ollama | اختياري لتحسين تجربة "آخر الجلسات" أو cache لاقتراحات متشابهة |

## ٦. مراجعة تدفق UX وتدفق النظام والتكامل

### ٦.١ تدفق المستخدم (UX)

- **الرئيسية → اقتراح:** وصف المسألة → زر "اقترح خوارزميات" → انتظار (بدون مؤشر تقدم واضح) → صفحة الاقتراحات.
- **الاقتراحات → النتائج:** زر "تشغيل محاكاة الأداء" → انتظار → صفحة النتائج مع جدول وتوصية.
- **النتائج / العودة:** "مسألة جديدة" → الرئيسية؛ أو من الرئيسية النقر على جلسة سابقة → `/session/{id}`.

نقاط التحسين: مؤشر تحميل أو skeleton أثناء انتظار Ollama والمحاكاة؛ رسالة واضحة عند تعطل Ollama (مع الحفاظ على النص إن أمكن).

### ٦.٢ تدفق النظام

- الطلبات كلها عبر نفس المصدر (Laravel)، بدون تفاعل فرونت-إند مع API خارجية مباشرة.
- التكامل الوحيد الخارجي: Laravel → Ollama (HTTP). عند عدم توفر Ollama تُعاد رسالة خطأ ولا يُحفظ شيء في الاقتراح.

### ٦.٣ التكامل

- **Laravel ↔ Inertia:** سليم؛ البيانات عبر props.
- **Laravel ↔ Ollama:** عبر `OllamaService` و`Http::` مع timeout؛ لا retry مدمج.
- **Laravel ↔ SQLite:** عبر Eloquent؛ التعامل مع غياب الجدول موجود في الـ Controller.

## ٧. الاختناقات والتناقضات وعدم الاتساق والكود غير المستخدم

### ٧.١ الاختناقات

- **Ollama:** طلب واحد طويل لكل من الاقتراح والتوصية؛ أبطأ عنصر في السلسلة.
- **المحاكاة:** تنفيذ متتابع لجميع المفاتيح في طلب واحد؛ يمكن أن يصبح بطيئاً إذا زاد عدد الخوارزميات أو الحجم.

### ٧.٢ تناقضات/عدم اتساق

- **اللغة:** الواجهة عربية و`locale` التطبيق `ar`؛ بعض رسائل الـ backend (مثل "تعذر الاتصال بـ Ollama") عربية، والتوصية قد تكون عربية أو إنجليزية حسب نموذج Ollama.
- **benchmark_key:** القائمة في الـ prompt ثابتة؛ أي مفتاح غير معروف في `BenchmarkRunner` يُعاد إلى `sorting` (default) دون تنبيه المستخدم.

### ٧.٣ كود غير مستخدم أو مربك

- **OllamaService::generate(..., true):** عند `stream === true` يُرسل طلب stream ولا تُستخدم نتيجته؛ ثم يُرسل طلب عادي. الاستدعاءات الحالية كلها `generate($x)` أي `stream = false`. يُفضّل إزالة فرع الـ stream أو تنفيذ streaming حقيقي وإرجاع النتيجة.

## ٨. خطة التحسين وخريطة إعادة الهيكلة والحديث

### ٨.١ خطة تحسين مختصرة

1. **أمان وتشغيل:** إضافة مصادقة (مثلاً Laravel Breeze) إذا كان التطبيق متعدد المستخدمين؛ إضافة rate limiting لـ `/suggest` و`/benchmark`.
2. **تجربة المستخدم:** مؤشر تحميل أو حالة "جاري التحليل" أثناء انتظار Ollama والمحاكاة.
3. **الكود:** إزالة أو تصحيح منطق `stream` في `OllamaService`؛ استخراج Form Requests للتحقق.
4. **الوثائق:** إنشاء مجلد `docs/` يتضمن: معمارية، سير العمل، متطلبات التشغيل، (وإن وُجد لاحقاً) توثيق API.

### ٨.٢ خريطة إعادة الهيكلة (مقترحة)

| المهمة | الأولوية | الجهد التقديري |
|--------|----------|----------------|
| Form Request classes للتحقق | منخفضة | صغير |
| استخراج مكونات مشتركة (Header, Card, Button) | منخفضة | صغير |
| إصلاح أو إزالة streaming في OllamaService | منخفضة | صغير جداً |
| إضافة مصادقة (Breeze/Fortify) | متوسطة | متوسط |
| إضافة rate limiting وحد أقصى لـ suggestions | متوسطة | صغير |
| نقل طلبات Ollama إلى Queue (اختياري) | منخفضة | متوسط |

### ٨.٣ خريطة التحديث (حديث التقنية)

- Laravel 12 و React 18 و Vite 7 و Tailwind 4 حديثة؛ لا حاجة فورية لترقية كبيرة.
- يمكن لاحقاً: إضافة TypeScript للواجهة، تفعيل مسارات API مع Sanctum إذا دعت الحاجة.

## ٩. تحليل فجوة الميزات وفجوة المنتج

### ٩.١ فجوة الميزات (مقارنة بسير العمل المستهدف)

- سير العمل الأساسي (وصف → اقتراح → محاكاة → توصية → حفظ) **مكتمل**.
- الفجوات: لا مصادقة، لا تصدير، لا اختيار حجم n من الواجهة، لا إدارة جلسات (حذف/أرشفة)، ولا وضع عمل بدون Ollama (مثلاً عرض تعقيدات فقط).

### ٩.٢ فجوة المنتج (منظور استخدام حقيقي)

- **استخدام شخصي/تعليمي:** المنتج كافٍ.
- **استخدام جماعي/مؤسسي:** يلزم مصادقة، وربما صلاحيات، وتحديد معدل الاستخدام.
- **تكامل مع أدوات أخرى:** يلزم API موثّق وربما مفتاح API.

## ١٠. خارطة الطريق والمراحل والملخصات العليا والمهام

### ١٠.١ المراحل المقترحة

| المرحلة | الهدف | المخرجات الرئيسية |
|---------|--------|---------------------|
| **المرحلة ١ (تحسينات فورية)** | استقرار وجودة كود | إصلاح/إزالة stream، Form Requests، حد أقصى لـ suggestions، وثائق معمارية أساسية في `docs/` |
| **المرحلة ٢ (جاهزية إنتاج أساسية)** | أمان وتجربة مستخدم | مصادقة، rate limiting، مؤشر تحميل، تحسين رسائل الخطأ |
| **المرحلة ٣ (توسع اختياري)** | مرونة وتوسع | API اختيارية، اختيار حجم n، تصدير، أو Queue لـ Ollama |

### ١٠.٢ ملخصات عليا (Epics) مقترحة

1. **جودة الكود والوثائق:** إصلاح الديون التقنية ووثائق المعمارية وسير العمل.
2. **الأمان والموثوقية:** مصادقة، rate limiting، ومعالجة آمنة للجلسات.
3. **تجربة المستخدم:** مؤشرات تحميل، رسائل خطأ أوضح، (اختياري) تصدير.
4. **قابلية التوسع (للمستقبل):** API، Queue، دعم قاعدة بيانات أخرى.

### ١٠.٣ قصص مستخدم نموذجية

- **كمستخدم:** أريد أن أسجّل دخولي حتى لا يرى أحد جلساتي.
- **كمستخدم:** أريد أن أرى أن النظام "يعمل" أثناء انتظار الاقتراح.
- **كمسؤول:** أريد تحديد عدد الطلبات لكل IP/مستخدم لتفادي إساءة الاستخدام.
